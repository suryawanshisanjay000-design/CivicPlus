CIVICPULSE — SINGLE BUILD PLAN FOR OPENCODE
============================================

PURPOSE
-------
Build a simple, working, demo-ready version of CivicPulse using OpenCode.

The original CivicPulse documents describe a production-grade municipal grievance
platform with:
- anonymous citizen reporting
- AI triage
- duplicate detection
- municipal officer dashboard
- SLA countdown/escalation
- before/after proof
- public tracking
- QR/PDF documents
- analytics

This plan deliberately reduces that large specification into a small, reliable MVP.
DO NOT try to implement every production-grade feature from the original documents.
The priority is:

1. Working end-to-end flow
2. Clean UI
3. Real database persistence
4. Real authentication for officials
5. Real Supabase storage
6. Real Groq triage if API key exists
7. Simple duplicate detection
8. SLA logic
9. Deployment-ready project
10. Easy live demonstration

SOURCE DECISIONS
----------------
The source documents propose a dual-portal system: anonymous Citizen Portal and
secure Municipal Official Portal. They also propose Groq AI triage, relational
database state management, duplicate clustering, SLA monitoring, closure proof,
and public tracking. These are the core concepts retained here.

The original architecture documents contain two database variants:
- PostgreSQL/PostGIS + Supabase
- MySQL 8.0 + Railway

For THIS SIMPLE IMPLEMENTATION, use ONE database architecture only:
SUPABASE POSTGRESQL.

Do not build both MySQL and PostgreSQL.
Do not add PostGIS unless it is already straightforward in the chosen Supabase setup.
Use normal latitude/longitude numeric fields and a simple Haversine-distance
calculation in application code for the MVP.

RECOMMENDED STACK
-----------------
Frontend:
- Next.js
- TypeScript
- Tailwind CSS
- Responsive UI

Backend:
- Next.js server-side/API routes OR a small FastAPI backend only if the existing

Database:
- Supabase PostgreSQL

Storage:
- Supabase Storage

Authentication:
- Supabase Auth for municipal officials
- Citizens do NOT need accounts

AI:
- Groq API
- AI is an enhancement, not a hard dependency
- If GROQ_API_KEY is missing, use a deterministic fallback triage function

Deployment:
- Frontend can be deployed to Vercel
- If the existing project already uses Railway for backend, keep Railway
- GitHub should contain the complete source code

MAP:
- Leaflet + OpenStreetMap if needed
- No paid map API required

PDF/QR:
- Keep simple
- Generate citizen receipt and optional work order only if reliable
- Do not let PDF generation block ticket submission

============================================================
2. CORE TICKET STATE MACHINE
============================================================

Use exactly these statuses:

SUBMITTED
    |
    v
ASSIGNED
    |
    v
IN_PROGRESS
    |
    v
RESOLUTION_SUBMITTED
    |
    v
RESOLVED

Additional:
BREACHED
REOPENED

Rules:
- New ticket starts as SUBMITTED or ASSIGNED after triage.
- Officer assignment changes it to ASSIGNED.
- Starting work -> IN_PROGRESS.
- Closing requires:
  1. minimum 20-character closing note
  2. after photo
- Successful closure -> RESOLVED.
- If SLA deadline passes before resolution -> mark BREACHED / record breach.
- Citizen may reopen a resolved ticket during the MVP review window if implemented.

Do NOT create a complicated event-sourcing architecture.
Use one ticket table plus one timeline/audit table.

-----------------------------
Only create this if assignment history is actually needed.
Otherwise keep assigned_officer_id in tickets and log changes in ticket_events.

============================================================
4. DATABASE SECURITY
============================================================

Supabase RLS must be enabled.

Citizen/public:
- Must NOT be able to read all tickets.
- Public tracking must expose only safe fields for a ticket verified by
  ticket number + secret PIN, or use a server-side endpoint that performs
  the verification.
- Do not expose officer email, internal notes, auth IDs, or sensitive data.

Officials:
- authenticated users can access tickets according to role.
- FIELD_OFFICER should only access permitted assigned/ward tickets.
- SUPERVISOR/COMMISSIONER can access broader data.

Never put:
- SUPABASE_SERVICE_ROLE_KEY
- GROQ_API_KEY
- other secrets
into frontend code.

============================================================
5. ANONYMOUS TICKET SECURITY
============================================================

When a citizen submits:

1. Generate a human-friendly ticket:
   CP-YYYY-XXXX

2. Generate a random 6-digit PIN.

3. Store only a secure hash of the PIN.

4. Return:
   - ticket_number
   - PIN ONCE
   - tracking URL

5. Show:
   "Save this PIN. It is required to access your ticket."

Do not claim the system is perfectly anonymous.
Say:
"No name, phone number, or email is required."

============================================================
7. AI TRIAGE
============================================================

Groq output must be strict JSON.

Expected shape:

{
  "department": "ROADS",
  "subcategory": "POTHOLE",
  "priority": "HIGH",
  "summary": "Large pothole creating accident risk",
  "urgency_score": 8
}

Allowed departments:
ROADS
WATER
SOLID_WASTE
ELECTRICAL
PUBLIC_HEALTH

Allowed priority:
LOW
MEDIUM
HIGH
CRITICAL

Rules:
- Validate AI output against allowed enums.
- If invalid, use fallback.
- If Groq fails, ticket creation MUST STILL WORK.
- Do not expose the Groq API key to the browser.
- Do not make the entire application dependent on AI availability.

Fallback logic example:
- pothole/road/crater -> ROADS
- water/leak/sewage/drain -> WATER
- garbage/waste/dumping -> SOLID_WASTE
- light/pole/wire/electric -> ELECTRICAL
- health/disease/public hygiene -> PUBLIC_HEALTH
- otherwise -> ROADS or OTHER default department

============================================================
8. DUPLICATE DETECTION
============================================================

MVP implementation:

When a new ticket has latitude + longitude:

1. Query active tickets in same department.
2. Calculate distance from new point to existing ticket points.
3. If distance <= 50 meters AND category/subcategory is similar:
   - show/record duplicate relationship
   - set duplicate_of to master ticket
   - increment master impact_count
   - do not create a second operational work order if practical

If implementing duplicate detection during submission is too risky:
- always create the citizen submission
- link it to an existing ticket afterward

IMPORTANT:
Never delete a citizen report just because it is a duplicate.
Preserve the submission for auditability.

============================================================
9. SLA ENGINE
============================================================

Every ticket receives:
sla_hours
sla_deadline

Suggested seed values:
- ELECTRICAL: 24 hours
- ROADS: 48 hours
- WATER: 24 hours
- SOLID_WASTE: 24 hours
- PUBLIC_HEALTH: 72 hours

Priority may shorten SLA only if explicitly implemented.

Dashboard:
- Green: > 50% time remaining
- Yellow: < 25%
- Red: overdue

Do not rely only on a frontend timer.
The server/database timestamp is authoritative.

For MVP, breach checking can happen:
- when dashboard loads
- when ticket is accessed
- when ticket is updated
- optionally through a scheduled backend job

Do not build complex distributed workers unless necessary.

============================================================
23. FAILURE-SAFE PRINCIPLES
============================================================

Rule 1:
If AI fails, ticket submission still works.

Rule 2:
If map fails, manual coordinates still work.

Rule 3:
If PDF fails, print-friendly HTML still works.

Rule 4:
If real-time connection fails, dashboard refresh still works.

Rule 5:
If image upload fails, show a clear error and do not silently create a
broken ticket.

Rule 6:
Never expose secret environment variables.

Rule 7:
Never silently discard a citizen submission.

25. OPENCODE EXECUTION RULES
============================================================

When executing this plan:

1. Inspect before editing.
2. Work in small phases.
3. After each phase, run the relevant tests.
4. Fix errors immediately.
5. Do not create duplicate files or duplicate architecture.
6. Reuse existing code whenever safe.
7. Keep dependencies minimal.
8. Prefer boring, reliable code over clever code.
9. Keep secrets server-side.
10. Never mark a feature complete without testing it.
11. If a feature is optional and is blocking the core flow, skip it.
12. Keep a RUNBOOK.md or DEVELOPMENT_STATUS.md showing:
    - completed
    - failed
    - blocked
    - next step
13. Before final response, run:
    - lint
    - typecheck
    - tests
    - production build
14. Report exact remaining issues rather than hiding them.
